## Current Trunk Foundation

Trunk is not an empty V2 baseline. It contains a selective historical backport
of the community registration model, subsequently updated for current Java and
Jakarta packages. Source history for `MpackManager` includes the original
AMBARI-21150/21231/21523 work, later V2 fixes through AMBARI-23254, the selective
Ambari 3-to-2.8 backport `a6536f3c6f`, and current modernization
`39112e4aea`. The following are present:

- `Mpack`, `Module`, `ModuleComponent`, and `ModuleDependency` metadata classes.
- `MpackManager`, `MpackResourceProvider`, the `/mpacks` resource wiring,
  `MpackEntity`/DAO, and fresh-schema `mpacks`/`stack.mpack_id` tables.
- Direct URL download, metadata parsing, module archive expansion, Stack
  compatibility symlinks, dynamic registration/deletion, and focused Java test
  source.
- Python execution-command accessors for mpack name/version and existing
  cluster/stack settings helpers.

It does not contain the community software registry, registry advisor, Mpack
Advisor implementation, instance-manager module, ServiceGroup types, V2
Blueprint package orchestration, or the community mpack installer/upgrade UI.

The retained registration code also has correctness gaps that cannot be treated
as completed community integration: request-global mutable `MpackManager.mpack`,
shared staging filenames, archive extraction without containment/link checks,
partial filesystem publication before database completion, exception stack
printing followed by a null create result, and registry-ID requests for which
trunk no longer resolves an mpack URI. These are source findings, not executed
failure tests. Necessary integration corrections belong with focused tests;
broader compiler/runtime-adapter hardening remains in R1+.

## Resolution Batches

The community branch is eight years behind current trunk and a direct comparison
contains broad unrelated source/dependency/frontend deletions. Provenance will be
preserved with an explicit community merge parent, but an unreviewed tree merge
is not itself the integration. The merge result will be resolved by the following
semantic batches, with current unrelated source retained and every community
capability accounted for above:

1. **W1-B1 build and provenance boundary.** Establish the explicit merge,
   preserve current root/module versions, JDK 17, Python 3, Jakarta, security
   upgrades, `ambari-server-spi`, `ambari-utility`, current service catalogs,
   frontend layout, and supported packaging. Add the instance-manager module only
   with current packaging conventions and required scriptlets.
2. **W1-B2 catalog and registration.** Reconcile the already-present model and
   registration API, then integrate registry/advisor metadata with current
   resource-provider and persistence conventions. Correct registration failures
   that prevent deterministic import/reload/retry.
3. **W1-B3 domain, API, and Blueprint projection.** Port package selection and
   topology orchestration through `(cluster_id, service_name)`. Exclude generated
   service IDs/ServiceGroups and record unsupported same-cluster duplicate types.
4. **W1-B4 Agent and instance manager.** Reconcile command producers/consumers,
   package install state, actual version reporting, Python 3 behavior, configured
   roots, legacy action compatibility, and package contents.
5. **W1-B5 lifecycle and upgrades.** Integrate package-aware change/version/state
   behavior while preserving repository catalogs, install actions, upgrade packs,
   provider ownership, and dependency/readiness limitations.
6. **W1-B6 UI.** Port only API-backed package flows into current Classic/React
   ownership after reading the relevant frontend-refactor baselines and both
   actual frontend sources. Preserve cluster routes, RBAC, workflow identity, and
   explicit platform capability gaps.

Each batch gets a separate `docs/mpack-v2/reviews/` checkpoint with exact paths,
provenance, validation results, and remaining gaps. More than 1,000 lines and
multiple functional modules are expected, so final candidate commits will be
split by coherent dependency/behavior boundaries unless an indivisible merge
boundary is justified.
